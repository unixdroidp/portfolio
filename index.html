🎣 PHISHING
Phishing Email — Credential Harvesting Attack
Tool: Email Header Analyzer + Browser Sandbox · Finding: Credential Harvesting
📋 Scenario

A user reported receiving a suspicious email claiming to be from the IT department asking them to reset their password via a link. The link directed to a fake login page mimicking the company's VPN portal.

📄 Sample Log / Evidence
EMAIL HEADER ANALYSIS
From: IT-Support <it-support@comp4ny-helpdesk.ru>
Reply-To: phish@malicious-domain.xyz
X-Originating-IP: 185.220.101.47  [TOR Exit Node]
Received: from smtp.mailgun-spoof.net
Subject: [URGENT] Password Reset Required — Action Needed
Link URL: http://corp-vpn-reset.xyz/login?id=U2Vj...
MX Record: mailgun-spoof.net → NOT company domain
SPF Check: FAIL
DKIM Check: FAIL  
DMARC Check: FAIL
🔧 Tools Used
📧 Email Header Analyzer 🌐 Browser Sandbox (Any.run) 🔍 VirusTotal 🛡️ WHOIS Lookup
🔍 Analysis Steps
  1. Extracted email headers using MXToolbox — identified spoofed sender domain
  2. Checked SPF/DKIM/DMARC records — all 3 failed (clear phishing indicator)
  3. Ran link through VirusTotal — flagged by 23/87 engines as malicious
  4. Opened URL in sandboxed browser — revealed credential harvesting login page
  5. Traced originating IP to TOR exit node (185.220.101.47)
  6. Cross-referenced domain registration — created 2 days before attack
✅ Final Conclusion
⚠️ CONFIRMED PHISHING — Credential Harvesting Attack

Attacker used a lookalike domain with spoofed IT branding to steal VPN credentials. Domain registered 48 hours before the attack — classic sign of a purpose-built phishing campaign.

🚨 Action Taken
🚫 Domain blocked at firewall level 🔑 Affected user password reset 📢 Security awareness alert sent 📋 Incident ticket raised (P1)
🎯 MITRE ATT&CK Mapping

🔨 BRUTE FORCE
Brute Force Login Attempt — Event ID 4625
Tool: Windows Event Viewer + Splunk · Finding: Automated Password Attack
📋 Scenario

SIEM alert triggered for 500+ failed login attempts (Event ID 4625) against a domain admin account within 3 minutes. Source IP was external, suggesting automated brute force attack targeting RDP (port 3389).

📄 Windows Event Log Sample
EVENT VIEWER — SECURITY LOG

Event ID:    4625 — An account failed to log on
Level:       Information
Date:        2026-04-15 02:17:43

Account Name: Administrator
Account Domain: CORP-DOMAIN
Logon Type:  10 (RemoteInteractive / RDP)

Source IP:   91.108.4.43 [Russia — ASN: AS62041]
Workstation: DESKTOP-TARGET01

[Count: 547 events in 3 minutes — 14:17:40 to 14:20:33]
[Pattern: Sequential, ~0.33s interval → Automated Tool]
📊 Splunk SPL Query Used
SPLUNK — SPL QUERY
index=windows_logs EventCode=4625
| stats count by src_ip, user, _time
| where count > 50
| sort -count
| eval threat_level=if(count>100,"CRITICAL","HIGH")
🔧 Tools Used
🖥️ Windows Event Viewer 📊 Splunk SIEM 🌍 AbuseIPDB 🔥 Windows Firewall
🔍 Analysis Steps
  1. Splunk alert triggered — threshold: >50 Event ID 4625 in 5 min window
  2. Filtered logs by source IP: 91.108.4.43 — 547 failures from single source
  3. Verified Logon Type = 10 (RDP) — remote attack confirmed
  4. Checked AbuseIPDB — IP reported 312 times for brute force activity
  5. Reviewed successful logins (4624) after brute force window — none found
  6. Checked account lockout policy — administrator account NOT locked (misconfiguration)
✅ Final Conclusion
⚠️ AUTOMATED BRUTE FORCE ATTACK — RDP Targeted

Automated credential stuffing tool (likely Hydra or Medusa) targeted the RDP service. Attack unsuccessful due to complex password policy, but account lockout policy gap identified.

🚨 Action Taken
🚫 IP blocked via firewall rule 🔒 RDP restricted to VPN only 🔐 Account lockout policy enforced 📋 Geo-blocking enabled (Russia/CN)
🎯 MITRE ATT&CK Mapping

✅ LOGIN TRACKING
Successful Login Analysis — Event ID 4624
Tool: Windows Event Viewer + Splunk · Finding: Suspicious After-Hours Login
📋 Scenario

Monitoring routine revealed a successful admin login (Event ID 4624) at 3:22 AM on a Saturday — outside normal working hours. The login came from an unfamiliar IP not in the employee's usual location.

📄 Windows Event Log Sample
EVENT VIEWER — EVENT ID 4624

Event ID:    4624 — An account was successfully logged on
Date:        2026-04-19 03:22:14 (Saturday)

Account Name:  john.admin
Account Domain: CORP-DOMAIN
Logon Type:  3 (Network)
Source IP:   103.21.244.0 [Dubai, UAE]
Process:     NtLmSsp (NTLM Authentication used!)

[!] Anomaly: Employee john.admin works 9AM–6PM IST
[!] Anomaly: Last known IP was 192.168.1.x (office)
[!] Anomaly: NTLM used instead of Kerberos (possible pass-the-hash)
📊 Splunk Correlation Query
SPLUNK SPL
index=windows_logs EventCode=4624
| eval hour=strftime(_time, "%H"), day=strftime(_time,"%A")
| where hour < 6 OR hour > 22
| where day="Saturday" OR day="Sunday"
| table _time, user, src_ip, LogonType
| sort -_time
🔧 Tools Used
🖥️ Windows Event Viewer 📊 Splunk SIEM 🌍 IP Geolocation 📞 User Verification
🔍 Analysis Steps
  1. Splunk after-hours login alert triggered for Event 4624 at 3:22 AM
  2. Source IP geolocated to Dubai — employee lives in Bangalore
  3. Logon Type 3 with NTLM auth flagged — Kerberos is standard in domain
  4. Called employee — confirmed NOT their login (account compromised)
  5. Reviewed post-login activity — accessed HR shared drive (data exfil risk)
  6. Correlated with recent phishing incident — credentials stolen 3 days prior
✅ Final Conclusion
🔴 CONFIRMED ACCOUNT COMPROMISE — Possible Data Exfiltration

Attacker used credentials stolen in prior phishing attack to log in remotely. NTLM usage suggests possible pass-the-hash technique. HR data accessed — DLP investigation initiated.

🚨 Action Taken
🔑 Account disabled immediately 🔐 All sessions terminated 🔍 DLP audit on accessed files 📋 P1 Incident raised + escalated to L2

TCP vs UDP
🔒 TCP — Reliable
  • 3-Way Handshake (SYN → SYN-ACK → ACK)
  • Guaranteed delivery + ordering
  • Slower but reliable
  • Used by: HTTP, HTTPS, SSH, FTP, RDP
  • SOC Note: Abnormal SYN floods = DoS attack
⚡ UDP — Fast
  • No handshake — fire and forget
  • No guarantee of delivery
  • Faster, lower overhead
  • Used by: DNS, VoIP, Streaming, DHCP
  • SOC Note: DNS tunneling exploits UDP 53
